Remaining name-based card identity (after the IDF-cosine engine migration)
==========================================================================

Context: the IDF-cosine pool engine (idf/idf2/idf3/idf4) and the affiliation
reweighting were migrated to key on stable cards_v2 UUIDs (the
`decklist-ids-data.json` corpus, bundled by setup-assets). The items below are
the name-keyed card-identity sites that remain, deliberately left out of that
scope. AGENTS.md requires keying every corpus/map/lookup on the UUID and
resolving the display name only at the final render boundary; 24 distinct
cards_v2 cards share a display name with another card, so a name key silently
merges them.


Issue 1 — the `decklists` pool variant still keys on display name
-----------------------------------------------------------------
src/draft/pool/variant-decklists.ts builds its own IDF corpus (`deckCorpus`)
from `poolData.decklists` (name arrays) and keys df / idf / cosine / the grown
pool on names. This is the same class of bug the idf/idf2/idf3/idf4 migration
fixed, but the `decklists` variant was outside that change.

Files:
  - src/draft/pool/variant-decklists.ts — `deckCorpus` reads
    `poolData.decklists`; switch it to `poolData.decklistIds ?? poolData.decklists`
    (already bundled) and resolve the grown counts back to display names at the
    return boundary via `resolveCountsToNames` (src/draft/pool/variant-idf.ts),
    exactly as the idf variants now do.
  - Lockstep mirror (AGENTS.md): scripts/spine-redundancy-experiment.mjs is a
    line-for-line re-port of the `decklists` internals and reads
    `public/decklists-data.json`; move it to the id corpus in the SAME change so
    its tuned constants do not silently desync.

Note: the `decklists` variant is not the default (tides4 is) and is not used by
any production pool path today, so impact is bounded; this is a consistency /
correctness cleanup.


Issue 2 — the pool engine's OUTPUT boundary collapses same-name cards
---------------------------------------------------------------------
The idf engine now scores internally on UUIDs, but it resolves back to display
names at its return boundary (`VariantResult.counts`, the idf3 provenance), and
everything downstream of the variant is name-keyed:
  - generate.ts caps and returns `counts: Map<cardName, number>`.
  - src/data/quest-content.ts resolves the pool against `ctx.nameIndex`
    (cardName -> cardNumber) in `resolvePool`, and keys the idf3 provenance
    summary (`buildDreamcallerProvenance`) on names via the same index.
  - The idf3 provenance public shape (`Idf3PoolProvenance.cardProvenanceByName`,
    src/draft/pool/types.ts; `Idf3ProvenanceSummary` in src/types/content.ts)
    and the "Why Cards" surface are name-keyed.

Consequence: when two distinct UUIDs that share a display name both land in one
pool, they collapse to a single card at this final resolution step (the name
index maps the shared name to one card number). The SCORING that builds the pool
is now correct; only the last name->cardNumber hop loses the distinction.

Fix (larger follow-up): push UUID-keyed counts through `resolvePool` using an id
index (id -> cardNumber, e.g. `buildIdIndex`) instead of `nameIndex`, and re-key
the idf3 provenance (`cardProvenanceByName` -> `...ById`) and the "Why Cards"
surface on UUIDs, resolving the display name only at render. This touches
generate.ts, quest-content.ts, src/types/content.ts, the provenance types in
src/draft/pool/types.ts, and the UI that reads the provenance, plus their tests.


================================================================================
Codebase-wide card-name-identity audit (2026-06-24)
================================================================================

The areas previously flagged "Not audited" (card rendering, merchant offers,
battle automation, journey signals, etc.) were swept for name-keyed card
identity. Coverage and results are summarized at the end ("Audit coverage").
The pool/affiliation findings above (Issues 1-3) are not repeated. The new
findings are Issues 4-14 below, ordered roughly by player impact.

In every case the defect is the same shape AGENTS.md warns about: a card's
DISPLAY NAME (`CardData.name`) is used as identity. 24 display names in
cards_v2.toml are each shared by two distinct UUIDs, so a name key, name match,
or name->id resolver silently merges those two cards or resolves to whichever
one happens to win a first-writer-wins lookup. Cards carry a stable UUID
(`id`) and a unique `cardNumber`; either is a correct key.


Issue 4 — dream-journey deck/catalog name helpers (the shared root primitives)
------------------------------------------------------------------------------
src/journeys/journey/shared/deckEntries.ts and viability.ts expose helpers that
locate or test deck/catalog cards by display name. Every named-card cost and
reward template (Issues 5-6) routes through them, so this is the root cause for
the bulk of the journeys findings.

Sites:
  - deckEntries.ts:32  findDeckEntriesByName            — `entry.card.name === cardName`
  - deckEntries.ts:60  findFirstDeckEntryIdByCardName   — takes `[0]` of the above
  - deckEntries.ts:72  findUntransfiguredDeckEntriesByName
  - deckEntries.ts:119 findTransfiguredDeckEntriesByName
  - viability.ts:71    deckContainsCardByName           — `card.name === cardName`
  - viability.ts:90    deckContainsUntransfiguredCardByName
  - viability.ts:124   deckContainsTransfiguredCardByName

Consequence: each returns deck entries for EVERY card sharing the rolled display
name, not the specific rolled card. Callers take `[0]`, so when two distinct
cards share a name the wrong card is the one mutated; viability gating can read
"viable" because a different same-name card is in the deck (or vice-versa),
producing no-op or mis-targeted options.

Fix: take a `cardId` (UUID) and filter on `entry.card.id === cardId`. The
sibling helpers `findDeckEntriesByPredicate` (deckEntries.ts:42) and
`projectedDeckEntries` (deckEntries.ts:12) already key on `entry.card.id` /
`entry.cardId` — mirror them.


Issue 5 — dream-journey COST templates resolve their target by name
-------------------------------------------------------------------
src/journeys/journey/shared/costs.ts. Each template `rollParams` stores
`pickFromList(...).name`, then `viable`/`apply` resolve back through the Issue-4
helpers, mutating the wrong same-name card:
  - costs.ts:581  purge_named_card               — apply: findDeckEntriesByName(p.cardName)[0]   (:603)
  - costs.ts:710  transform_card_to_random_pool  — apply: findFirstDeckEntryIdByCardName(p.cardName) (:730)
  - costs.ts:1120 remove_transfiguration_from_card — apply: findDeckEntriesByName(p.cardName) (:1135/1139)

Fix: store the rolled card's `id` in params and resolve via id-keyed helpers;
resolve the display name only inside `render`.


Issue 6 — dream-journey REWARD templates resolve target/grant by name
---------------------------------------------------------------------
src/journeys/journey/shared/rewards.ts. Catalog grants go through
`resolveCardIdByName` (rewards.ts:313 — `cards.find(card => card.name === name)?.id`,
first match wins); deck targets go through the Issue-4 helpers. Templates:
  - rewards.ts:1218 gain_named_card                       (resolveCardIdByName, :1232)
  - rewards.ts:1408 apply_named_transfiguration_to_card_name (findUntransfiguredDeckEntriesByName, :1441)
  - rewards.ts:1614 change_card_to_become_type            (findFirstDeckEntryIdByCardName, :1638)
  - rewards.ts:1867 purge_named_starter                   (findDeckEntriesByName, :1887)
  - rewards.ts:1978 transform_starter_into_named_card     (resolveCardIdByName, :1996)
  - rewards.ts:2009 transform_card_in_deck_into_named     (findFirstDeckEntryIdByCardName + resolveCardIdByName — wrong source AND target)
  - rewards.ts:2120 duplicate_named_card_X                (findDeckEntriesByName[0], :2140)
  - rewards.ts:2870 make_card_reclaim                     (findDeckEntriesByName[0], :2888)
  - rewards.ts:2942 opening_hand_grant_for_X_battles      (deckContainsCardByName gate, :2957)
  - rewards.ts:2965 temporary_card_copy_for_X_battles     (deckContainsCardByName gate, :2980)
  - rewards.ts:3483 paramsTargetStarterCard               (meta conflict check via params.cardName -> findDeckEntriesByName, :3487)

Consequence: grants/creates the wrong card UUID, or removes/transfigures/
duplicates/reclaims the wrong same-name deck card. (The last two are gated and
currently no-op in `apply`, so today only their viability gate and rendered name
are wrong; they become full mis-targets when `apply` is implemented.)

Fix: same as Issue 5 — carry the card `id` through params; resolve catalog
grants by `cards.find(c => c.id === id)`.


Issue 7 — journey param-builders and operation selectors carry/resolve names
----------------------------------------------------------------------------
These produce the name-keyed params Issues 5-6 consume:
  - src/journeys/journey/shapes/one_target_many_operations/fill.ts:110-139,663 —
    `rewardParamsFor` emits `{ name: target.card.name }` / `{ cardName: target.card.name }`.
  - src/journeys/journey/shapes/one_operation_many_targets/fill.ts — `metaRewardParams`/
    `isMetaRewardPair` build `{ name }` / `{ cardName }` / `{ oldCardName, newCardName }`
    from `targetName(target)` (the display name).
  - src/journeys/journey/operationBuilders.ts:296-339 — when a value carries
    `cardName`/`targetCardName`/`oldCardName`, it builds a selector with
    `names: [value.cardName]` and `selection: "exact"`, matching the wrong
    same-name card. (Sibling `cardId`/`targetCardId`/`oldCardId` branches are
    correct.)

Fix: thread `target.card.id` through these builders (`{ cardId }` /
`{ oldCardId, newCardId }`); the `target` object already carries the resolved
card, so `.id` is free. Prefer the id selector branches and retire the
`names:` fallback.


Issue 8 — temporary bane grant resolves the GRANTED card by name (player-facing)
--------------------------------------------------------------------------------
This is the only confirmed player-facing wrong-card GRANT in the audit.
  - src/journeys/journey/shared/costs.ts:114  resolveBaneCardId — `cards.find(card => card.name === baneName)?.id`
  - src/state/multiplayer-quest-context.tsx:4130 pushTemporaryBaneGrant — calls
    resolveCardByName (helper at :439, `candidate.name === cardName`, first match),
    then writes that card's `cardNumber` into real DeckEntry rows (:4159).

Consequence: a dream-journey bane cost names a bane card; if its display name
collides with any other card, the player receives the WRONG card (wrong UUID,
wrong rules) into their deck. Reachable through normal dream-journey play.
Removal later is safe (keyed on `entryId`); only the grant is corrupted.

The sibling mutations `addCardById` (:3580), `addCardByIdWithTransfiguration`
(:3637), `addBaneCardById` (:3698) already resolve via `resolveCardById` (UUID,
:427) — the correct pattern. `pushTemporaryBaneGrant` / `resolveCardByName` is
the lone name-resolving grant.

Fix: have the journey cost layer carry the bane card's UUID and have
`pushTemporaryBaneGrant` accept and resolve a UUID via `resolveCardById`,
keeping `baneName` only as a log/display label.


Issue 9 — referenced-card hover previews resolved by name
---------------------------------------------------------
src/journeys/ui/referencedCards.ts:107 `findReferencedCardPreviews` builds
`new Map(cards.map(card => [card.name, card]))` (last-writer-wins) and resolves
quoted card names scraped from journey text against it (:110). A name shared by
two cards collapses to one entry, so the hover preview (JourneyScreen.tsx
referencedCards -> JourneyHoverCard) can show the wrong card's art/rules.

Fix: this site is inherently name-driven (it parses display names out of
rendered text). The clean fix is to emit structured UUID card references
alongside the text and resolve those; at minimum, return all cards matching the
name instead of silently collapsing to one.


Issue 10 — Dreamcaller editor resolves signature cards by name
--------------------------------------------------------------
src/editor/DreamcallerDetailView.tsx:392-418 builds `byName`
(`new Map<name.toLowerCase(), CardData>`, last-writer-wins, :403-406) and
resolves the Dreamcaller's `signatureCards` name array against it (:410).

Consequence: when two cards share a display name the editor's live signature-
card panel renders the wrong card, or marks a real signature "unresolved".

Fix: the component already exposes `signatureCardIds` (index-aligned UUIDs;
src/types/content.ts:33, populated at src/data/quest-content.ts) and already
builds `cardsByUuid` (:432). Resolve signatures via `signatureCardIds` +
`cardsByUuid` instead of `signatureCards` + `byName`.


Issue 11 — non-default draft pool variants count/key on card name
-----------------------------------------------------------------
Outside the idf/decklists engine already covered by Issues 1-3:
  - src/draft/pool/pool-data.ts:53-76 populates `core` (Set), `archLists`,
    `draftLists` with `card.name`, and builds `cardIdByName` first-writer-wins
    (:66 — the second same-name UUID is unreachable through it).
  - src/draft/pool/variant-diverse.ts:64-92 — `themeBreadth`/`colorBreadth`
    (`Map<string, number>`) count breadth over those name strings, so two
    same-name cards merge into one breadth bucket, corrupting the down-weight
    signal that drives selection in the `diverse` variant.
  - src/draft/pool/variant-picksig.ts:90-107 — `resolveSignatureToCorpus` maps
    signatures into corpus UUID space via the name-keyed `cardIdByName`, so a
    collided-name signature anchors on the wrong UUID or fails to resolve.

Impact is bounded: these feed the non-default `diverse`/`seed`/`picksig`
variants, not the default `tides4` production path.

Fix: populate `core`/`archLists`/`draftLists` with `card.id` and re-key the
breadth/reach maps on UUID; pass `signatureCardIds` directly into corpus space.


Issue 12 — production tide artifacts baked from name-keyed IDF corpora
----------------------------------------------------------------------
  - scripts/bake-tides.mjs:570 calls `buildPoolData(cards, decklists)` without
    the 4th `decklistIds` arg, so `idfCorpus` (:571) keys the IDF table and
    decks on card NAMES; clustering (kMedoids), the favored-tide assignment, the
    signature-probe cosine (:618), and the name->id resolution (`idByName`,
    first-writer-wins, :565) all run in name space. Bakes data/tides.jsonc, read
    by the `?algo=tides`/`tides2` production variants.
  - scripts/seed-tide-relationships.mjs:474 has the same omission; the ally
    cosine and per-Dreamcaller tide probe (`probeNames`, :510) run in name
    space and bake data/tides2_relationships.jsonc (production `tides2`).
    Mitigant: one-off seeder, `--force`-gated, hand-curated afterward.

Consequence: two same-name cards merge into one IDF token, conflating
frequency/co-occurrence and corrupting the clustering, the tide assignment, and
the baked artifact; a collided name resolves to an arbitrary UUID.

Fix: load public/decklist-ids-data.json and pass it as the 4th `buildPoolData`
arg so the corpus keys on UUIDs; resolve id->name only for the baked `name`
field. (Mirrors the bake-tides3/4 sigseed scripts, which are already
UUID-keyed.)


Issue 13 — merchant corpus cluster graph degraded by a UUID->name->UUID round-trip
----------------------------------------------------------------------------------
scripts/bake-merchant-corpus.mjs:454-461. `buildDraftRecords` returns
`r.mainboard` as display NAMES (already resolved from UUID); the script then
maps them BACK to UUIDs through the lossy first-writer-wins
`cardMaps.nameToId.get(name)` (:458) and builds the cluster graph
(`computeMultiplicityAndDf`, `buildClusterGraph` -> df/idf/adjacency/clusters)
over the round-tripped ids. For any of the 24 collided names the back-resolution
lands on an arbitrary UUID, merging distinct cards in the cluster-graph half of
the production data/merchant_corpus.json. (The quality-fit half is clean — it
uses `r.packIds`/`r.pickIds` directly.)

Fix: have `buildDraftRecords` expose mainboards as UUIDs directly (it resolved
them from UUIDs) and consume those instead of round-tripping through `nameToId`.


Issue 14 — offline / ingestion-boundary name keying (lower priority)
--------------------------------------------------------------------
  - scripts/apply-archetype-tides.mjs:12-67 builds `cardNameToTides`
    (`Map<cardName, Set<tide>>`) and patches cards_v2.toml by matching
    `name = "..."` lines, so same-name cards both receive the merged tide union.
    Low severity: one-off migration that writes only the legacy `tides` field.
  - scripts/setup-assets.mjs:425 (and the identical scripts/lib/card-refs.mjs:36)
    `buildCardMaps` builds `nameToId` first-writer-wins; `buildDraftRecords`/
    `buildDecklists` resolve raw name tokens from cubecobra source data through
    it, so a collided name in name-only source data resolves to one arbitrary
    UUID. This is the intended legacy ingestion path (raw data has only names),
    but it is the upstream origin of the UUIDs the "good" scripts trust, so
    Issue 13's merge ultimately traces here. Not independently fixable without
    disambiguated source data (e.g. cardNumber-tagged decklists).
