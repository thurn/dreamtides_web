Task 30 QA — observations

1. Dev-scene reload nuance: `?goto=<scene>` re-derives a fresh scene on every
   full page reload rather than resuming the existing one.

   Cause: the bootstrap effects in src/App.tsx fire on mount while the coop fold
   still holds the seeded genesis state (dreamcaller === null), so their
   `state.dreamcaller !== null` early-return does not yet see the reloaded run.
   They therefore dispatch another LOAD_STATE, and `loadState`
   (src/rules/quest/lifecycle.ts) unconditionally replaces the quest slice, so
   the later-sequenced bootstrap wins and the battle/scene is re-rolled (e.g.
   the opponent changes between reloads).

   Scope: this only affects the developer QA bootstrap flag. Real play does not
   carry `?goto`, so reloading mid-battle (reached via a battle site) re-folds
   the SAME battle cleanly — verified in Task 30 QA scenario 3 on a plain
   `?game=` tab (opponent unchanged across reload).

   Note: before Task 30's append-readiness fix (src/coop/hooks.ts) this
   mount-time bootstrap dispatch silently rejected ("LogClient not ready"), so a
   reload happened to preserve the prior battle by accident. The fix makes the
   intended one-shot bootstrap actually apply; the reload re-derivation is the
   visible trade-off on the dev flag. A future reload-safe guard would gate the
   bootstrap effects on the room's confirmed log being empty (head === 0) rather
   than on the pre-fold `state.dreamcaller`.

Cumulus clean PlayMode gate — wall-clock-sensitive panel travel assertion

- On the first clean-library verification of point-lit glass, unrelated
  `CumulusPanelTravelTests.ToggleDestination_ReachesBothExactAnchorsInReferenceDuration`
  measured the 420 ms travel at 601 ms after all glass tests passed. The same
  full PlayMode assembly had passed repeatedly against the warm library. The
  test compares wall-clock coroutine duration with a ±20 ms tolerance, so an
  editor/graphics hitch can fail behavior whose final anchor is correct. Replace
  the wall-clock assertion with deterministic stepped-time evidence or separate
  the curve-duration contract from host scheduling latency.

Cumulus site-render logging — site adapters are reported as legacy

- `src/components/ScreenRouter.tsx` derives `servedByCumulus` only from
  `cumulusScreenFor(screen)`. A top-level `site` screen always resolves to null
  there because site implementations are selected later through
  `cumulusSiteScreenFor(site)`. Production `screen_rendered` entries therefore
  report `servedByCumulus: false` for registered Cumulus sites, including the
  Duplication screen verified through `?goto=duplication`. Resolve the active
  site before logging and use the same site-registry decision that renders the
  route.
