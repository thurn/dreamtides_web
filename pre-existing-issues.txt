Name-based card identity in the IDF / affiliation pool engine
=============================================================

Context (shared by all entries below): 24 distinct cards_v2 cards share a
display name with another distinct card (different UUIDs, different rendered
text and rules). AGENTS.md requires identifying cards by stable UUID, never by
name. The draft-record bundle already carries id-aligned fields (`mainboardIds`,
`packIds`, `pickIds`, `signatureCardIds`) so consumers can key on ids.

Already migrated to UUID identity:
  - Rendering paths (so the wrong card is NEVER shown to a player):
      src/components/PoolViewer.tsx, src/battle/integration/opponent-deck.ts
      (signature seeds), src/screens/QuestStartScreen.tsx.
  - The record-replay / fit-model family now keys its corpus, idf, prior, and
    co-occurrence on lowercased card ids and translates card numbers through a
    `numberToId` / `idIndex` boundary: src/draft/replay/fit-model.ts,
    src/draft/replay/draft-records.ts, the buildFitModel / buildReplayDraftState
    wiring in src/data/quest-content.ts (fed `mainboardIds` / `packIds` /
    `signatureCardIds`), its internal readers (src/battle/integration/coherence.ts,
    opponent-deck.ts pack source + cohesion, src/journey_v2/signals/fit.ts), and
    the offline mirror scripts/draft-replay-experiment.mjs (ported in lockstep;
    recall@4 held at ~79-80% — slightly higher because the 24 collisions no longer
    blend). The replay signature path now reads `signatureCardIds`.

What remains is the POOL idf-cosine engine, which still keys its corpus on
display name. Impact is bounded and non-visual: a same-name collision blends two
cards' document-frequency / affinity, slightly perturbing steering weights. It
never renders the wrong card.

Hard constraints that apply to every issue below:
  - Lockstep rule (AGENTS.md): an engine and its offline tuning mirror must move
    in the SAME change. Migrating one without the other silently desyncs the
    tuned constants / metric the mirror produces.
  - The pick-data variants (`pickfit`/`pickearly`/`pickpos`/`pickchoice`/
    `pickcohere`/`picksig`) are ALREADY id-keyed (quest-content feeds them
    r.packIds / r.pickIds), so they are NOT part of this work.
  - The fit-model family is done (see above); it shares ONLY the pure `idfCosine`
    helper with the pool engine, and that helper is already key-agnostic
    (src/draft/idf-fit.ts treats keys as opaque strings), so the work below is
    independent of it.


Issue 1 — Pool idf-cosine corpus (idf / idf2 / idf3 / idf4 + affiliations)
--------------------------------------------------------------------------
One atomic unit: idf2Corpus wraps idfCorpus, and idf3 / idf4 / affiliation-weights
all read that same base corpus, so re-keying idfCorpus forces them to move
together — you cannot ship "idf3 on UUIDs" while idf2 stays on names.

Files:
  - src/draft/pool/variant-idf.ts        — idfCorpus builds the IDF corpus from
    poolData.decklists (name arrays); idfCosine is already key-agnostic.
  - src/draft/pool/variant-idf2.ts       — idf2Corpus wraps idfCorpus (near-twin
    diversity weights).
  - src/draft/pool/variant-idf3.ts       — signature probe vs name-keyed idf, AND
    the provenance surface (signatureCardNames / distinctiveCardNames) which is
    shown in the UI: it must key internally on ids but resolve DISPLAY names from
    the id only for the provenance summaries.
  - src/draft/pool/variant-idf4.ts
  - src/affiliations/affiliation-weights.ts — resolves signature UUIDs to names,
    then scores in the name-keyed corpus; score directly on ids instead.
  - Provenance types in src/types/content.ts and the buildDreamcaller*Provenance
    functions in src/data/quest-content.ts that surface idf3 by-name maps.
  - Offline mirrors to move in lockstep: scripts/similar-pool.mjs and
    scripts/idf3-*.mjs (and any other idf-pool tuning script).
  - Tests: variant-idf.coherent.test.ts, variant-idf3.provenance.test.ts,
    variant-idf3.starter-deck.test.ts, affiliation-weights.test.ts, and any
    others that pin name-keyed pool behavior.

Asset-pipeline change required: /decklists-data.json (built by
readAdaptedRecordDecklists in scripts/lib/card-refs.mjs) is name-only today. The
pool corpus needs an id-keyed source — either bundle id arrays alongside the
names in that artifact, or feed poolData id-keyed decklists from another source.
Note the decklists set is NOT identical to the fit-model corpus: decklists keeps
every seat with a non-empty mainboard, while buildDraftRecords requires exactly
30 trimmed picks, so the two corpora differ and cannot simply share one feed.

Signature-id cleanup (fold in here): generateDreamcallerPool in
src/data/quest-content.ts still passes dreamcaller.signatureCards (names) into
the idf3 / sigseed signature inputs. sigseed's corpus is already id-keyed (it
uses the pick-corpus + poolData.cardIdByName); idf3's is not. Once idfCorpus is
id-keyed, pass the already-loaded dreamcaller.signatureCardIds instead.

Verification: the coherent-growth oracle tests (variant-idf.coherent.test.ts pin
idf3 against the idf2 oracle) plus `npm run tides-similarity`. Per AGENTS.md, do
not add tests that pin specific production card names or TOML-derived content.
