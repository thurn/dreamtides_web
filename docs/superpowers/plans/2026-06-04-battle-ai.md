# Battle AI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use super-subagent-driven-development (recommended) or super-executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a local, suggestion-engine AI opponent for the journey prototype's playable battle that plays a fixed Starter deck competently, proposes every action for explicit human approval, and stays under a 100ms per-decision budget.

**Architecture:** A shared "rules spine" (`src/battle/engine/`) supplies challenge resolution, an energy ramp, and turn handoff as pure functions that emit existing `BattleDebugEdit` commands. A new module tree (`src/battle/ai/`) holds a lightweight forward model, per-card knowledge for the ten Starter cards, a static evaluation function, a staged beam-search planner, an abstract opponent-response model, and a driver that turns the next planned action into a proposed `BattleCommand[]`. A React hook (`use-battle-ai.ts`) and a proposal bar (`BattleAiProposalBar.tsx`) surface one proposal at a time; only the human's Approve click dispatches. The AI never mutates state directly and introduces no new command types.

**Tech Stack:** TypeScript, React, Vitest (unit tests), Node `--experimental-strip-types` (headless self-play harness), `agent-browser` (browser QA). Authoritative spec: `docs/journey_prototype/battle_ai.md`. Rules: `docs/battle_rules/battle_rules.md`.

## Architectural Decisions (read before starting)

These reconcile the spec against the actual code. They are binding; do not re-derive them.

1. **Exhaustion is forward-model-only.** The engine's `BattleCardInstance` has no `exhausted`/awakened field (`markers` is only `{ isPrevented, isCopied }`). The rules-doc concept of "exhausted the turn played, awakens at Dawn" is **not** engine state. The AI's forward model tracks per-character "can challenge this turn" itself. The judgment resolver and "declare challengers" operate purely on which characters occupy `deployed` (`D0`–`D3`) slots; there is no challenger/defender flag in state.

2. **The judgment resolver is a pure proposal function, not an engine mutation.** It does **not** populate `BattleTransitionData.judgment` on a debug-edit transition (debug edits don't auto-resolve combat). It returns a `BattleJudgmentResolution` (for display) **plus** the ordered `BattleDebugEdit[]` that commit the outcome (`ADJUST_SCORE` for the scoring side; `MOVE_CARD_TO_ZONE` to the void for each dissolve). The human approves, then those edits dispatch through the normal `APPLY_COMMAND` path. Reuse the existing `BattleJudgmentResolution`/`BattleLaneJudgment` types from `src/battle/engine/result.ts` as the proposal's shape.

3. **Effective spark = base + support, computed by the caller.** `selectEffectiveSparkForInstance(instance)` (in `src/battle/state/figments.ts`) gives base spark (`printedSpark × figmentCount + sparkDelta`). Support and "+X✦ per ally" are **not** applied by the engine. The pure adjacency map lives in `engine/support.ts`; the actual +✦ contributions come from the AI's per-card models (Phase 3) and the forward model. The Phase 1 judgment resolver accepts an optional `supportContribution` map (empty for an unmodeled board), so it ships on base spark and gains Support once card models exist.

4. **`aiMode` threading.** `runtimeConfig` is currently **not** passed to `PlayableBattleScreen` (only `site` is) and **not** passed into `createBattleInit`. Phase 5 adds `aiMode` to `RuntimeConfig`, `CreateBattleInitInput`, and threads it through `BattleSiteRoute` → `useEnsureBattleSession` (deck injection) and → `PlayableBattleScreen` (hook + UI).

5. **`BattleAiChoiceTrace` gains two optional fields.** The existing trace (`src/battle/types.ts:401`) has no plain-language rationale and its `targetSlotId` is a slot, not a card — insufficient for "Flashpoint Blast on your 3✦ body." Add `rationale?: string | null` and `targetBattleCardId?: string | null`. Both optional, so the existing clone (`src/battle/state/transition.ts:74`, spread `{ ...choice }`) and normalize (`src/battle/multiplayer/battle-normalize.ts:136`, `?? []`) need no change.

6. **Phase ordering uses the rules-doc set.** `BattlePhase` includes `"dawn" | "day" | "dusk" | "night" | "challenge" | "ending"`. Use these (ignore the legacy `startOfTurn`/`main`/etc. members).

### Task 1.2: Judgment resolver

**Files:**
- Create: `src/battle/engine/judgment.ts`
- Test: `src/battle/engine/judgment.test.ts`

Resolves the Challenge phase for one active side. Signature:

```ts
export interface JudgmentInput {
  state: BattleMutableState;
  activeSide: BattleSide;
  // Optional +✦ to add to a battleCardId's base spark (Support/static). Empty for an unmodeled board.
  supportContribution?: ReadonlyMap<string, number>;
}
export interface JudgmentProposal {
  resolution: BattleJudgmentResolution; // reuse type from engine/result.ts (lanes, playerScoreDelta, enemyScoreDelta)
  edits: BattleDebugEdit[];             // ADJUST_SCORE + MOVE_CARD_TO_ZONE(void) to commit
}
export function resolveJudgment(input: JudgmentInput): JudgmentProposal;
```

Per-lane rules (apply `battle_rules.md` §Challenge phase resolution, lanes `D0`→`D3` in order): effective spark = `selectEffectiveSparkForInstance(instance) + (supportContribution.get(id) ?? 0)`. Compare the active side's challenger in `deployed[Dx]` against the opposing defender in the same `Dx`:
- Both present: lower spark dissolves (→ void); equal sparks dissolve both; figment stacks lose top-down via `selectFigmentChallengeLossCount(instance, opposingSpark)` (move that many — for the prototype, dissolve the whole instance when the count ≥ its figment count, else leave it). A defended challenger does **not** score.
- Only the active challenger present (unpaired): it scores its effective spark for the active side (`scoreDelta` on that lane, accumulated into the active side's `*ScoreDelta`).
- Only the defender present: nothing.

Build `edits` as: one `ADJUST_SCORE { side: activeSide, amount: totalScored }` (omit if zero), then a `MOVE_CARD_TO_ZONE` to the void destination for each dissolved `battleCardId`. (See `BattleDebugZoneDestination` in `commands.ts` for the void destination shape.)

- [ ] **Step 1: Write the failing tests.** Specify by the bug class each catches — incorrect combat math and wrong dissolve/score sets. Cover, as separate `it` blocks built on small hand-constructed `BattleMutableState` fixtures (use a `makeJudgmentState` helper that places named instances in given slots with given sparks):
  - **Lower spark dissolves, no score:** challenger 4✦ vs defender 3✦ in D0 → defender dissolved, challenger survives, score delta 0.
  - **Tie dissolves both:** 3✦ vs 3✦ → both in void, delta 0.
  - **Unpaired scores spark:** challenger 4✦ in D1, no opposing defender → `activeScoreDelta === 4`, nobody dissolved.
  - **Only defender present:** nothing happens, no edits.
  - **Support shifts the result:** challenger base 3✦ with `supportContribution {id→2}` vs defender 4✦ → challenger (5) wins, defender dissolves. Catches: support not being added before comparison.
  - **Figment top-down:** a figment-stack challenger resolved via `selectFigmentChallengeLossCount` matches the rules-doc worked example. Catches: wrong figment loss count.
  - **Edits commit the proposal:** the returned `edits` contain exactly the dissolve moves + one `ADJUST_SCORE` equal to `resolution`'s active-side delta. Catches: resolution/edits divergence (the bug that would let display and committed state disagree).
- [ ] **Step 2: Run to verify failure.** FAIL (module/function missing).
- [ ] **Step 3: Implement `resolveJudgment`.** Pure; no mutation of `input.state`.
- [ ] **Step 4: Run to verify pass.**
- [ ] **Step 5: Commit & push.**
