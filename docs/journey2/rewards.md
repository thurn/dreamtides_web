# Journey V2 Reward Generation

Journey v2 rewards are generated by the Dream Merchant encounter system in
`src/journey_v2`. A merchant site reads the current quest state, identifies deck
needs, builds rewards that answer those needs, selects two offers, prices them
in essence, and renders the resulting offers as the merchant encounter.

The system is deterministic for the same quest seed, site, resources, deck
contents, held Dreamsigns, and content bundle. Card identity is carried through
UUIDs and deck entry IDs; display names are presentation text.

## Reward Surface

Every generated encounter contains exactly two offers, with offer IDs `A` and
`B`. Each offer has one reward, one essence price, a locked state, and the
reward objects the UI should show. A reward is selectable when it has either a
direct application payload or a choice request whose candidates each have an
application payload.

Choice rewards ask the player to choose a concrete object inside the reward:

- `grant_support_card` presents three to five catalog cards and adds the chosen
  card to the deck.
- `grant_dreamsign` presents two to four available Dreamsigns and grants the
  chosen Dreamsign.
- `replace_weak_with_fit` presents three to five catalog cards, removes the
  weak deck entry, and adds the chosen replacement card.

Direct rewards apply immediately after the player accepts the offer:

- `grant_exact_card` adds one ranked catalog card.
- `transfigure_card` applies one transfiguration to one deck entry.
- `purge_weak_card` removes one deck entry.
- `duplicate_keystone` duplicates one deck entry.
- `gain_essence` adds essence, clamped by the current essence capacity.
- `raise_essence_cap` increases essence capacity.
- `add_reclaim_to_event` gives one event Reclaim 1.
- `add_fast_to_event` makes one event fast.
- `reduce_reclaim_cost` lowers one event's Reclaim cost by one, to a minimum
  of one.
- `convert_event_to_role` changes one deck entry between Event and Character to
  fill an event or character role gap.

## Inputs

Reward generation starts from a merchant context built from the current quest
state and content bundle:

- Quest seed and current site identity.
- Current essence and essence capacity.
- Current deck entries, resolved to card data by card number and UUID.
- Held Dreamsign IDs and fallback names.
- The full card database.
- The full Dreamsign template list.
- Buildaround support metadata keyed by card UUID.
- The draft fit model, when present in quest content.

The catalog card pool contains non-starter, non-special cards from the content
bundle. By default, catalog card rewards avoid card UUIDs already present in the
deck. Dreamsign candidates exclude held Dreamsign IDs and held fallback names.

## Need Detection

The deck read emits needs. Each need has a kind, a stable need ID, severity,
confidence, score, observation text, references to real card objects where
relevant, and a list of compatible reward builders.

Needs are scored as severity multiplied by confidence, after both values are
clamped to the range from zero to one. The final need list is ordered by score,
then severity, then confidence, then stable need ID.

The current need kinds are:

- `under_supported_payoff`: a deck card's support metadata says it needs a
  theme, and the deck's support share for that theme is below the target. The
  target varies by support tier. The need appears when adequacy is below 0.6.
- `missing_role`: the deck is short on one of the role checks: draw, recursion,
  interaction, cheap early play, events, characters, abandon outlet, or
  finisher. Required counts are derived from deck size and the role.
- `curve_problem`: the deck is top-heavy or short on cheap early characters.
  Top-heavy decks are detected from average cost and count of high-cost cards.
- `upgrade_target`: a deck entry has at least one eligible transfiguration that
  improves the effective card. The read keeps the best transfiguration for each
  entry and returns up to two upgrade targets.
- `weak_card`: a deck entry has low contribution to the current deck. Bane
  entries are excluded, and a card that is the sole support for a detected
  payoff theme is protected from this need.
- `dreamsign_gap`: a fallback need when Dreamsign candidates are available and
  the deck has cards.
- Broad support and deck-fit fallback needs: theme needs that keep the encounter
  buildable when the main read produces fewer than two needs.

After primary needs are detected, two conflict rules are applied:

- A weak-card need for a deck entry is suppressed when the same entry is also
  an under-supported payoff.
- A missing abandon-outlet need is suppressed when an under-supported abandon
  payoff is already present.

The read then adds fallback needs only until it has at least two needs. This is
why a merchant encounter can still produce two offers in decks with few obvious
problems.

## Reward Construction

For each need, the catalog first tries the need's compatible reward builders in
order. Duplicate builder IDs on the same need are ignored. Builders that cannot
produce a valid reward for that need return no reward.

After the compatible builders, generation tries a fallback builder list for
each need:

- `transfigure_card`
- `purge_weak_card`
- `grant_dreamsign`
- `gain_essence`
- `raise_essence_cap`

This fallback pass adds buildable candidates without creating duplicates for
the same need, builder, and target. It is the reason resource rewards and
Dreamsign rewards can appear as backup offers on theme needs even when they
were not the first compatible builder.

Catalog card ranking is deterministic. Candidate cards are scored by role match,
support fit, curve fit, fit-model relevance, and rarity value, then tied by a
stable hash of quest seed, site ID, need ID, and card UUID. A card must have
some match score, except when ranking replacement candidates for a weak-card
need. Starter cards, special cards, and already-owned card UUIDs are excluded
from the normal grant pool.

Dreamsign ranking is also deterministic. Dreamsigns score higher when their
text appears to answer the need's role or theme, then tie by the same stable
seed/site/need/object hash.

## Offer Selection

The encounter builds a flat candidate list from all needs and buildable rewards.
Candidates without any application payload are filtered out. The first offer is
the selectable candidate with the best base rank.

Base rank sorts by:

- Need rank.
- Reward rank within that need.
- Higher need score.
- Higher need severity.
- Stable need ID, reward builder ID, and target key.

The second offer is selected from the remaining candidates by distinctiveness
from offer `A`, then by base rank. Distinctiveness adds weight for a different
need ID, different need kind, different target key, and different reward
builder. This makes the second offer prefer a materially different decision
when one exists.

The target key depends on the need:

- Card needs key by deck entry ID and card UUID.
- Missing-role and curve needs key by theme and role.
- Dreamsign-gap needs key by Dreamsign ID.

The generated encounter is valid only when two offers are selected. The offers
are ordered as `A`, then `B`.

## Pricing And Locked Offers

Every selected reward receives an essence price. The price starts from the
reward's value essence, then multiplies by need severity, reward scarcity, and
market jitter.

Need severity lowers the merchant's price for more severe needs. The multiplier
ranges from 1.12 for severity zero to 0.9 for severity one.

Scarcity combines these factors:

- Reward family: card grants, Dreamsigns, transfigurations, duplicates, purges,
  essence rewards, and other rewards each have a family multiplier.
- Rarity: Legendary card rewards are priced higher; Special card rewards are
  also higher when a reward references that rarity.
- Choice count: chooser rewards get a small multiplier as their candidate count
  rises.
- Broad catalog reach: chooser rewards get a small multiplier when they expose
  a larger share of the catalog.
- Outside-pool status: the pricing function supports it, though current
  generated merchant rewards pass current-pool rewards.

Market jitter is a deterministic hash-based multiplier from quest seed, site
ID, offer ID, and reward builder ID. It ranges from 0.95 to 1.08.

Positive-value rewards have a minimum price of 25 essence. Price is capped by
the current essence capacity. An offer is locked when the price is above current
essence, or when the reward has positive value and the current essence capacity
is below the minimum price. Locked offers remain visible and carry the
`insufficient_essence` locked reason.

## When Each Reward Appears

### `grant_support_card`

This appears for under-supported payoff, missing-role, and curve-problem needs.
It requires at least three ranked catalog candidates after excluding starter,
special, and already-owned card UUIDs. It is most likely when the deck lacks a
role such as draw, recursion, interaction, cheap early play, events,
characters, an abandon outlet, or a finisher, or when a payoff card's support
theme is underrepresented.

For role needs, cards rank higher when their text or type directly matches the
missing role. For payoff and theme needs, cards rank higher when their support
metadata supports the needed theme. For curve needs, cheap character cards rank
higher.

### `grant_exact_card`

This appears for under-supported payoff, missing-role, and curve-problem needs
when the need confidence is at least 0.75 and at least one ranked catalog card
exists. It grants the single highest-ranked catalog card instead of asking the
player to choose from several cards.

It can appear for high-confidence role and curve problems, and for
under-supported payoff needs with a clear best matching card.

### `grant_dreamsign`

This appears for Dreamsign-gap, under-supported payoff, and missing-role needs.
It requires at least two available Dreamsign templates after excluding held
Dreamsigns. It can be produced by a need's compatible builder list, and it is
also one of the fallback builders.

Dreamsigns rank higher when their effect text appears to answer the current
need: draw text for draw needs, Reclaim or void text for recursion needs,
banish/prevent/enemy text for interaction needs, cost/energy/character text for
cheap early play, and matching support-theme text for under-supported payoff
needs.

### `transfigure_card`

This appears for upgrade-target needs. The target deck entry must still exist,
and the read must have selected a beneficial transfiguration projection for
that entry. The reward displays the target deck entry with a preview card and a
badge for the transfiguration.

Upgrade-target needs are generated from effective card state. A deck entry with
an existing transfiguration is skipped. Eligible improvements include cost
reduction, spark improvement, draw text, Reclaim text, numeric improvements,
trigger improvements, activated ability discounts, and Prismatic improvements,
depending on what the card is eligible to receive.

### `purge_weak_card`

This appears for weak-card needs. The target deck entry must still exist. The
reward removes that deck entry.

A weak-card need is generated only when the deck has at least four cards, the
candidate is not a Bane, the candidate is not protected as sole support for a
payoff theme, and its contribution score is low enough. Starter cards and low
synergy cards are more likely to become weak-card targets.

### `replace_weak_with_fit`

This appears for weak-card needs when at least three ranked replacement catalog
cards exist. It removes the weak deck entry and adds the chosen replacement
card. Replacement candidates use the same card-ranking machinery as support
card grants, with weak-card needs allowed to keep ranked candidates even when
the match score is otherwise zero.

This reward appears when the system finds a weak card and the catalog can offer
enough replacement choices.

### `duplicate_keystone`

This appears for under-supported payoff needs. The target payoff deck entry
must still exist. It duplicates the referenced deck entry.

This reward appears when a payoff card is asking for more support for one of
its metadata themes. It reinforces the payoff itself rather than adding support
around it.

### `gain_essence`

This appears for theme needs. It is part of the fallback builder list, so it can
appear when a theme need needs a buildable backup offer. Accepting it adds 50
essence, clamped by current essence capacity.

It can appear on missing-role, curve-problem, Dreamsign-gap, and broad fallback
needs because those are theme needs. It does not appear for card-target needs
such as weak-card or upgrade-target needs.

### `raise_essence_cap`

This appears for theme needs. It is also part of the fallback builder list.
Accepting it increases essence capacity by 75.

It can appear in the same situations as `gain_essence`: missing-role,
curve-problem, Dreamsign-gap, and broad fallback needs.

### `add_reclaim_to_event`

This appears for recursion role needs. The deck must contain at least one Event
whose base card has no Reclaim cost. The selected event is the best deck event
by Legendary status, then higher energy cost, then entry ID. Accepting it adds
Reclaim 1 to that deck entry.

This reward appears when the read says the deck is light on recursion and the
deck contains an event that can receive Reclaim.

### `add_fast_to_event`

This appears for interaction role needs. The deck must contain at least one
Event whose base card is not fast. The selected event uses the same best-event
ranking as Reclaim rewards. Accepting it makes that deck entry fast.

This reward appears when the read says the deck is light on interaction and the
deck has an event that can be quickened.

### `reduce_reclaim_cost`

This appears for recursion role needs. The deck must contain at least one Event
whose base Reclaim cost is greater than one. The selected event uses the same
best-event ranking as the other event modification rewards. Accepting it lowers
that event's Reclaim cost by one, to a minimum of one.

This reward appears when the deck needs recursion and already has a costly
Reclaim event that can be made easier to replay.

### `convert_event_to_role`

This appears for missing-role needs whose role is `events` or `characters`.
For an events need, the deck must contain a Character to convert into an Event
with subtype Rite. For a characters need, the deck must contain an Event to
convert into a Character with subtype Visitor. The first matching deck entry is
selected.

This reward appears when the deck is short on one of those broad card-type
roles and has the opposite type available for conversion.

## Acceptance Path

When the player accepts an offer, the encounter is regenerated from the current
state and content, then the request is checked against the regenerated offer.
The encounter signature, offer ID, price, reward builder, need ID, locked state,
and any required choice all have to match the current generation result.

If the offer is valid and affordable, the price is paid first, then the reward
payload is applied. Composite rewards apply their child payloads in order. The
merchant site is then marked complete and the quest returns to the dreamscape.

Declining an offer also regenerates and validates the encounter. A valid decline
marks the site complete and returns to the dreamscape without applying a reward.
