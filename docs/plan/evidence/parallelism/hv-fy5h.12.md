## Proposed typed seams (not current APIs)

E-CONTRACT should introduce only the bounded contracts required to dispatch separate modules, using existing branded identities and `Ability`, `Variant`, `BattleView`, `PolicyDecision`, `PolicyContext`, `Action`, `Prompt`, `Answer`. Validate the final names/shapes after `.3`; do not freeze an invented evaluation API in this audit.

- AST: `features(abilities: readonly Ability[], variant: Variant) → AbilityFeatures`, with separate immediate/conditional/modal/deferred contribution records for draw, energy, points, spark, removal reach, recursion, tempo and trigger value; unknown dynamic expressions are represented as qualified terms, not silently exact zero. No state mutation/engine effects are executed to extract features.
- Dusk: `assign(view, side, legal, services) → { next: Action; projectedConceded: number; projectedLostValue: number; ... }`, using injected card valuation/projection and finite budget service. The solver owns exact layout/sequence reasoning; its next action is validated against legal moves. Integrator re-evaluates from the next actual view rather than persisting mutable React flow or stale plans.
- Valuation/Day: functions over fair view/decision/context + injected AST/Dusk/evaluation services return ranked `PolicyChoice` candidates and strategy reasons. Response valuation belongs here; actual Prompt answers belong E-PROMPT. Cost/placement/X/mode choices use the prompt boundary, not card-name keys or a new top-level action schema.
- Prompt: `answer(view, prompt, services) → Answer`, with injected feature/card value/evaluation and fair deck sampling only where necessary. It preserves `isLegalAnswer`, optional-chain finite/loopable handling, and covers the full discriminated prompt union.
- Search: `(view, decision, ctx, immutableConfig, expert/evaluation) → SearchResult`, containing choice plus existing trace fields **without requiring a new runtime PolicyId**. C-PREP wraps completed algorithms into real `Policy` instances/IDs and final traces. Each algorithm can implement its own bounded prefix-plus-fallback AnswerSource in its owned module; only create a shared helper if a concrete duplicate consumer and separate owner are proved. Nested rollouts charge one documented work budget and cannot independently reset deadlines or recurse unboundedly through Planner/Expert.
