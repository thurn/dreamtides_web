- Ladder: existing normative Counters and contextual X rules settle source locality, clearing, actual in-play storage, zero, and shared X. No D/C/P entry adds another rule for these UUIDs. Read-only Rust searches of battle_rules.md and the rules_engine source find no stored-counter value/payment implementation supplying this missing rule.
- Payment-departure retention: ladder step 4, adapted narrowly from official Comprehensive Rules 113.7a and 608.2h, effective September 25, 2026 (https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.txt). An ability is independent of its source; a resolving source-information request can use last-known information. The native finite scalar-transport admission applies this to source departure during that activation's own payment. Capture the count immediately before that removal, after previous printed-order counter payments. This does not extend generic zone, queued-trigger, floating, source-spark, or later-response retention. For an activation without a payment-departure snapshot, Dreamtides' explicit clearing rule supplies 0 after a later response removes the source. A source back in play supplies its current count.
- Shared X: default minimum 1, with min 0 for the two meaningful zero-spark dissolve clauses. The chosen X bounds targets before payment, survives payment, and agrees with every other X payment. The amount paid is distinct from the source's remaining count. Fixed counters and each variable counter payment share one finite source budget; energy changes affect only energy. Counter-X is mandatory and top-level so its numeric preparation precedes targets, following the existing abandon-X authoring boundary. Fixed optional and alternative counter payments retain printed order and normal feasibility checks. Directly authored nested counter-X is unplayable.
- Printed store clauses remain source-local: self-abandonment and response removal store nothing. Liminal Dreamer's hand discard may pay an empty hand, and its draw reads its live source count without spending counters or adding a once-per-turn limit. Existing loop handling applies.
- Implementation boundary: one ValueExpr, one PaymentCost, existing chooseX prompt role, an optional source-payment scalar on activated stack items, strict saved scalar validation and viewer-qualified projection. No new prompt, event, floating, history, route, or status kind.
