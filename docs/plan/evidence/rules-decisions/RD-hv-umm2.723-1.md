# RD-hv-umm2.723-1: Copiable card ability type references

- Ladder: C12 directly; step 5 for runtime bindings, evaluation order, copiable Variant inheritance and ambiguous canonical figments.
- rules.md: § Ability Types → Card ability type remapping.
- Affects: 3d86f8ce-42ac-43dc-96d5-121e6d1a6167 (consumer retained by hv-umm2.270).
- Why: C12 applies the chosen type to literal ability references and eligible figment creation, preserving the card’s own subtype and the original creation spark. The existing copiable Variant travels with captured and created copies, so its remap travels with it; an independent plain creation has no remap. Mapping the original expanded abilities preserves variant-specific behavior and paired instruction references. A later instruction’s chosen-type placeholder is a binding, not a literal character type. Different figment identities can share a subtype. A designated canonical target takes precedence over unmarked synthetic candidates; a false designation excludes a special figment from the target set. Without a designated target, a unique implicit candidate is supported. Multiple selected canonical targets are invalid and refuse evaluation. This preserves the ordinary Warrior target alongside the distinct Warrior-subtype Legionnaire, without selecting by name or order.

The historical Rust/client record for the same UUID has different text and supplies no applicable implementation precedent. The official Magic Comprehensive Rules analog inspected for parent hv-umm2.270 distinguishes type words from names (612.2) and persistent resolving effects (611.2a), but its ordinary copy exclusion for text changes (707.2) does not establish Dreamtides copy inheritance. C12 and the explicit step-5 interpretation above govern this engine representation. This ruling does not set journey acquisition lifetime, repeat-gain ordering or UI behavior.
